# Does Failure Context Improve AI-Generated Bug Fixes?

COMP 3520 (Software Engineering) research assignment, Idea 5: *AI debugging from failing JUnit tests*.

[![CI](https://github.com/amirJazybayev/comp3520-ai-debugging-research/actions/workflows/ci.yml/badge.svg)](https://github.com/amirJazybayev/comp3520-ai-debugging-research/actions/workflows/ci.yml)

**Research question.** When a large language model (LLM) is asked to repair a Java bug exposed by a failing JUnit test,
does adding the execution diagnostics (assertion messages, exception types, project stack frames, compiler errors) to the
prompt improve how often it produces a correct repair, compared with giving it only the faulty code and the failing test?

| Condition | What the model sees | Feedback after a failed attempt |
|---|---|---|
| `baseline` | buggy class (with Javadoc specification) + failing visible test source | "does not compile" / "test still fails" |
| `diagnostics` | the same, plus the Surefire test execution output | the same, plus the new test or compiler output |

Each patch is compiled and run against the **visible** test (shown to the model) and an independent **hidden** test
class (never shown). A *plausible* repair passes the visible test; a *correct* repair also passes the hidden tests.
Plausible-but-not-correct patches are counted as **overfitting**.

## Repository layout

```
benchmark/          Maven project: 15 reference (correct) classes, visible tests, hidden tests
bugs/bugs.json      bug manifest: id, class, fault category, fault description
bugs/bNN/*.java     single-fault buggy version of each class
repair/             Python harness (stdlib only)
  llm.py            OpenAI-compatible chat client (OpenAI, Gemini, Groq, OpenRouter, Ollama, ...)
  prompts.py        prompts for the two conditions + extraction of the patched class
  maven.py          runs Maven/JUnit, parses Surefire XML, builds the diagnostics text
  experiment.py     `validate` the benchmark, `run` the experiment
  analyze.py        session table, metrics, McNemar test, manual-review template
  junit_summary.py  renders JUnit XML as a table in the GitHub Actions job summary
tests/              pytest unit tests + integration tests (real Maven build)
results/runs/       raw results: config.json, attempts.jsonl, every model reply and patch
results/            summary.md, sessions.csv, manual_review.csv (generated by analyze)
report/             report outline and lab notebook
.github/workflows/  CI: all unit, JUnit and integration tests, with result tables in the job summary
```

## Setup

Requirements: JDK 17+, Maven 3.9+, Python 3.10+.

```powershell
python -m pip install -r requirements-dev.txt
```

## Reproduce

1. **Check the benchmark** (every reference passes all tests, every buggy version fails its visible test):

   ```powershell
   cd benchmark; mvn -B test; cd ..
   python -m repair.experiment validate
   ```

2. **Run the unit tests**:

   ```powershell
   python -m pytest -v
   ```

3. **Configure a model.** Any OpenAI-compatible endpoint works. Examples:

   | Provider | `LLM_BASE_URL` | `LLM_MODEL` (example) |
   |---|---|---|
   | Google Gemini (free tier) | `https://generativelanguage.googleapis.com/v1beta/openai` | `gemini-2.5-flash` |
   | Groq (free tier) | `https://api.groq.com/openai/v1` | `llama-3.3-70b-versatile` |
   | Ollama (local, free) | `http://localhost:11434/v1` | `qwen2.5-coder:7b` |
   | OpenAI | `https://api.openai.com/v1` | `gpt-4o-mini` |

   ```powershell
   $env:LLM_BASE_URL = "https://generativelanguage.googleapis.com/v1beta/openai"
   $env:LLM_API_KEY  = "<your key>"
   $env:LLM_MODEL    = "gemini-2.5-flash"
   ```

   Never commit API keys. Optional: `LLM_TIMEOUT` (seconds per call, default 300) and `LLM_REASONING_EFFORT`
   (e.g. `low`, for "thinking" models that are slow to answer). Both are recorded in each run's `config.json`.

4. **Run the experiment** (15 bugs x 2 conditions x 3 repeats, up to 3 attempts per session):

   ```powershell
   python -m repair.experiment run --repeats 3 --max-attempts 3
   ```

   A pilot on two bugs: `python -m repair.experiment run --bugs b01,b04 --repeats 1`.
   Raw output goes to `results/runs/<run-id>/`.

5. **Analyse**:

   ```powershell
   python -m repair.analyze
   ```

   Writes `results/summary.md`, `results/sessions.csv` and `results/manual_review.csv`.

## Benchmark

All 15 bugs were written for this study (no third-party code), which reduces the risk that the model has memorised
them (a known threat for public benchmarks such as QuixBugs or Defects4J). Each bug is a single-fault edit of a
small, documented class; categories are listed in [bugs/bugs.json](bugs/bugs.json). The Javadoc of each class is the
specification: the visible and hidden tests were written from it, not from the model's output.

## Continuous integration

Every push runs [ci.yml](.github/workflows/ci.yml):

- **Harness unit tests (Python)**: pytest with a fake LLM, no network.
- **Benchmark**: `mvn test` on the reference implementations (all visible + hidden JUnit tests),
  `repair.experiment validate`, and integration tests that run the harness against the real Maven build.

Per-test result tables appear in each run's **Summary** page, and the raw reports are uploaded as artifacts.
